# Frontend вебсайта «ЗАРЯ»

Проект официального имиджевого и коммуникационного сайта игры **«ЗАРЯ: Марш Революции»**. Проект включает публичный сайт, административную CMS и отдельный интерфейс модерации комментариев. Приложения работают с общим серверным API.

> **Состояние проекта:** создан локальный frontend-каркас трёх React-приложений. Настроены npm workspaces, Vite, ESLint, CheckJS, Vitest/React Testing Library и конфигурация Playwright. Реализован первый участок: список новостей `/news`, пагинация, состояния загрузки/ошибок, API-слой и MSW. Остальные бизнес-функции ниже остаются целевыми. Реальный backend и SQL отсутствуют; интеграция с сервером не проверена.

## Планируемые возможности

**Публичный сайт:** информация об игре, FAQ, новости, обновления и списки изменений, PressKit с ZIP-архивом, регистрация, вход, профиль, комментарии и реакции к новостям. Адаптивная работа начиная с ширины 320 px.

**CMS:** отдельное React-приложение для роли `Admin`. Создание, редактирование, удаление, сохранение черновиков и публикация новостей и обновлений; загрузка допустимых изображений.

**Модерация:** отдельное React-приложение для роли `Moderator`. Просмотр комментариев и удаление с подтверждением.

**Вне объёма текущей версии:** почтовый сервис, подписки, формы подписки, отправка уведомлений и связанные элементы CMS. Email в учётной записи сохраняется как данные пользователя, но отправка писем не реализуется.

## Технологии и ответственность

| Часть | Стек | Кто меняет |
| --- | --- | --- |
| Три frontend-приложения | React, JavaScript/JSX, Vite | Разработчик frontend |
| Проверки frontend | ESLint, TypeScript CheckJS + JSDoc, Vitest, React Testing Library, Playwright | Разработчик frontend |
| Таблицы `News`, `Updates` | Microsoft SQL Server, отдельные T-SQL-скрипты | Разработчик frontend/закреплённых таблиц |
| Backend | ASP.NET Core + Entity Framework Core | **Другой разработчик**; в этой работе **только чтение** |
| Таблицы `Users`, `Comments`, `NewsReactions` | Microsoft SQL Server | **Другой разработчик**; в этой работе **только чтение** |

**Принцип:** один репозиторий, но не общая ответственность за каждый файл. Изменение серверного кода, конфигурации, миграций EF Core или чужих таблиц в рамках этой работы **запрещено**. Проблемы интеграции передаются разработчику backend.

Подробнее: [ARCHITECTURE_Frontend.md](ARCHITECTURE_Frontend.md). Для кодирующих агентов: [AGENTS_Frontend.md](AGENTS_Frontend.md).

## Статус согласований

Внутренние договорённости и границы ответственности приведены ниже. Общий README содержит описание проекта и технического состояния.

Здесь «согласовано с владельцем проекта» означает решение, явно одобренное пользователем, который ведёт разработку frontend в этом репозитории. Это не означает согласование с разработчиком backend. Подтверждения серверного контракта от backend-разработчика пока нет.

| Решение | С кем согласовано | Статус и область действия |
| --- | --- | --- |
| Один репозиторий, папки `Frontend` и `Backend` | С владельцем проекта | Принятая структура; серверная часть ведётся другим разработчиком |
| Три отдельных приложения React + JavaScript/JSX + Vite; npm workspaces, CheckJS/JSDoc | С владельцем проекта | Принятая архитектура frontend; общая библиотека UI или переход на TypeScript не согласованы |
| Полное исключение подписок, рассылок и почтовых уведомлений; email учётной записи сохраняется | С владельцем проекта | Граница текущего функционального объёма |
| Независимая разработка с MSW и центральными обработчиками в `Frontend/mocks` | С владельцем проекта | Разрешена в явном mock-режиме разработки и тестах; production не активирует моки |
| Первый этап: `/news`, список, пагинация, загрузка, пустое состояние, ошибки и тесты | С владельцем проекта | Реализован; следующий функциональный этап пока не выбран |
| `GET /api/news`, параметры, DTO и ошибки | С владельцем проекта как предварительное предложение | Используется во frontend/MSW; требует отдельного согласования с backend-разработчиком |
| Официальная интеграция `msw/vite` | С владельцем проекта при условии совместимости | Условие проверено, интеграция реализована; worker в `public` не размещается |
| Реальные адреса API, cookie/CORS/CSRF, роли и остальные серверные контракты | Требуется frontend + backend-разработчик; изменения требований также утверждает владелец проекта | Открытые вопросы, не подменяются поведением моков |
| Физические схемы `News`/`Updates`, совместимость с EF Core и применение DDL | Требуется согласование с владельцем backend/БД | SQL-скрипты и миграции текущим этапом не затрагиваются |

Frontend-разработчик отвечает за интерфейсы, API-слой, моки и frontend-проверки. Backend-разработчик отвечает за серверные endpoint, бизнес-логику, безопасность, EF Core, миграции и серверное хранение. Владелец проекта утверждает объём этапов и существенные изменения архитектуры. Frontend-работы не дают разрешения изменять серверную часть или применять изменения к общей БД.

Применение официального `msw/vite` одобрено при совместимости: MSW 3.0.3 и Vite 8.3.5 совместимы, плагин используется. Следующий функциональный этап, серверные контракты авторизации, cookie/CORS/CSRF и SQL-схемы ещё не согласованы. Успешный mock-сценарий не считается подтверждением серверной возможности.

## Порядок реализации frontend

1. Согласовать небольшой участок: ожидаемое поведение, предварительный контракт при отсутствии API, изменяемые файлы и проверки. Важные архитектурные изменения и новые зависимости обсудить до реализации.
2. Описать DTO через JSDoc в `src/api`, реализовать запрос и обработку ответа. Компоненты используют API-слой независимо от режима запуска.
3. Подготовить только необходимые обработчики и вымышленные данные в `Frontend/mocks`. Не добавлять условные успешные ответы и тестовые роли в рабочие компоненты.
4. Реализовать загрузку, успех, пустые данные, ошибки и повторную попытку; учитывать отмену запросов и сохранение введённых или уже загруженных данных.
5. Запустить `npm run check` из `Frontend`. Отдельно согласовать длительные браузерные и интеграционные проверки. Обновить README и документацию в объёме поручения, отметить результат проверок и оставшиеся неопределённости.

При готовности backend сверить контракт совместно с его разработчиком и подключить конкретную операцию к реальному API. Backend, EF Core, серверные миграции и SQL не менять для обхода несовместимости. Обнаруженный блокер сразу сообщить владельцу проекта с описанием причины и вариантами решения.

## Локальная разработка

### Предпосылки

- Git.
- Node.js 24.x и npm >=11. Версии пакетов зафиксированы в `package.json` и `package-lock.json`; рекомендуемая линия Node указана в `.nvmrc`.
- Доступ к согласованному backend API или его тестовому имитатору для разработки UI.
- Для проверки SQL - разрешённый тестовый экземпляр Microsoft SQL Server (не общая рабочая БД без согласования).

### Команды

Все npm-команды выполняются из `Frontend`. Из корня репозитория (для воспроизводимой установки использовать `npm ci`):

```powershell
cd Frontend
npm ci
npm run dev:web
npm run dev:cms
npm run dev:moderation

npm run lint
npm run typecheck
npm run test:unit
npm run build

# Отдельная, более тяжёлая проверка:
npm run test:e2e
```

`npm run check` последовательно выполняет ESLint, CheckJS, Vitest и сборку. Dev-серверы привязаны к `127.0.0.1`: web на 5173, CMS на 5174, moderation на 5175. Порты фиксированы; занятый порт приводит к ошибке. Сборки находятся в `Frontend/apps/<имя>/dist`.

Playwright подготовлен для проверки оболочек и ширин 320/768/1024/1440. Перед первым согласованным запуском требуется `npx playwright install chromium`. Команда `npm run test:e2e` самостоятельно запускает три dev-сервера. Браузеры автоматически при установке проекта не устанавливаются.

Главная содержит ссылку на `/news`. Страница новостей загружает данные через API-слой. При ошибке следующей страницы карточки сохраняются и повторяется та же страница. CMS и модерация остаются закрытыми; авторизация, редактирование материалов и загрузка файлов не реализованы.

### Конфигурация API

Frontend должен брать адрес API из конфигурации окружения (например, `VITE_API_BASE_URL`). В первом участке используется предварительная переменная `VITE_API_BASE_URL` (по умолчанию `/api/`, включает API-префикс). Cookie и авторизация этим этапом не определяются и требуют согласования с серверным разработчиком.

Не записывать пароли, ключи и другие секреты в frontend-переменные `VITE_*`: их значения могут оказаться в браузерной сборке. Не добавлять реальные `.env` с секретами в Git.

Сервер запускается по инструкции владельца backend. Этот README **не предполагает права изменять или запускать его конфигурацию** без согласования.

## Требования к интерфейсу

- Публичный сайт работает от **320 px**; CMS и модерация ориентированы на ширину **от 1024 px**.
- Сетка новостей/обновлений: **4 карточки от 1440 px**, **3 карточки на 768-1439 px**, **1 карточка до 767 px**.
- Навигация на публичном сайте сворачивается в меню при ширине менее **1024 px**.
- На главной - до трёх последних опубликованных новостей и обновлений; раскрытие описания игры без запроса к API.
- Регистрация, вход, профиль, комментарии, реакции и права доступа проверяются также на сервере.
- Дизайн: тёмный фон, белый текст, жёлто-оранжевые и фиолетовые акценты, мотивы карт и территориальных границ.

Точные критерии, в том числе валидация полей, обработка ошибок и временные показатели, приведены в `ARCHITECTURE_Frontend.md` и исходном ТЗ.

## Тестирование и приёмка

В обычной работе проверяем затронутый frontend статическим анализом (ESLint + CheckJS), быстрыми тестами (Vitest) и тестами компонентов (React Testing Library). Для браузерных сценариев и адаптивности предусмотрен Playwright. Долгие E2E, визуальные и нагрузочные тесты выполняются отдельно, по согласованию.

Ключевые сценарии: регистрация, авторизация, редактирование профиля, новости и обновления, кнопка «Показать ещё», комментарии, реакции, CMS, загрузка JPEG/PNG/WebP (до 5 МБ), модерация, проверка ролей, отсутствие сети, HTTP 503, экраны шириной 1440/1024/768/320 px. Проверка почтовой подписки исключена из текущей приёмки вследствие согласованного изменения объёма.

SQL-скрипты `News`/`Updates` тестируются **на отдельной разрешённой БД**; их применение к общей БД координируется с разработчиком backend.

## Разработка новостей с MSW

Из `Frontend` выполнить `npm run dev:web:mock`, затем открыть `/news`. Обычный запуск не активирует MSW. Режим определяется `vite --mode mock` и отслеживаемым `.env.mock`; включение дополнительно ограничено `import.meta.env.DEV`. Производственные сборки, включая сборку с `--mode mock`, не подключают обработчики. Плагин `msw/vite` обслуживает worker без файла в `public`; копирование других публичных ресурсов не отключается.

Центральные данные и обработчики находятся в `Frontend/mocks`, JSDoc-контракт в `apps/web/src/api/news.contract.js`. MSW запускается до React. Неизвестные запросы внутри выбранного API-origin и API-префикса блокируются с явной ошибкой; запросы ресурсов Vite и приложения проходят.

`VITE_MOCK_SCENARIO` выбирает `default` (26 вымышленных новостей), `empty`, `slow` (1500 мс), `error` (503), `network-error` или `next-page-error` (503 после первой страницы). Неизвестное имя останавливает mock-запуск. Установить переменную можно в локальном `.env.local` или окружении терминала; `.env.example` содержит образец. Материалы не описывают реальную игру. Данные формируются заново при перезагрузке; состояние серверной сессии не моделируется.

Подробный предварительный контракт приведён в разделе 8.3 архитектурного документа. MSW подтверждает сценарии интерфейса, но не совместимость с реальным backend, cookie, CORS или CSRF.

Production-сборка публичного приложения автоматически проверяется `Frontend/scripts/verify-web-build.js` на отсутствие mock-worker, маркеров MSW и вымышленных данных.
