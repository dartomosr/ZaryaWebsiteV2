# Правила работы над Frontend ZaryaWebsite

## 1. Перед изменениями

Прочитать [README проекта](../README.md), [инструкцию разработки](README.md), [архитектуру](docs/ARCHITECTURE.md), [требования](docs/REQUIREMENTS.md) и относящийся к задаче код. При переносе кода прочитать [план миграции](docs/MIGRATION.md); при интеграции изучить [OpenAPI](../ApiContracts/README.md) и [исторический документ интеграции](../Backend/BACKEND_INTEGRATION.md). Последний не заменяет актуальные схемы API.

Общаться на русском, использовать понятные имена и читаемый код. Существенные изменения архитектуры, стека и объёма обсуждать до реализации. Описание целевой архитектуры само по себе не разрешает миграцию кода: её объём согласуется отдельной задачей. MIGRATION.md является временным: после базового переноса сначала актуализировать архитектуру, README, требования и ADR, затем удалить план и все ссылки на него.

## 2. Границы ответственности

**Серверная часть доступна только для чтения.** Не изменять ASP.NET Core, контроллеры, сервисы, DTO, модели, EF Core, миграции, серверные настройки, deployment или инфраструктуру, косвенно перенастраивающую backend. Общее поручение «починить интеграцию» не отменяет запрет.

Если необходима серверная доработка, остановить затронутую часть, сообщить конкретную несовместимость и варианты, предложить запрос ответственному backend-разработчику. Не создавать обходы или фиктивный успех. При блокере сообщать о нём своевременно и продолжать независимую разрешённую работу.

Разрешённая зона: frontend-приложения, их тесты, ресурсы, инструменты и относящаяся к задаче документация. Документ интеграции в Backend изменять только по отдельному поручению на документацию; исправление ссылок при согласованном переносе документов не разрешает менять серверные контракты или код.

Отдельные T-SQL-скрипты допустимы только для News и Updates в согласованной frontend-директории. До написания согласовать имена, типы, PK/FK, индексы, каскады, модель секций, даты, статусы и совместимость с EF Core. Это не миграции EF. Users, Comments, NewsReactions и остальные таблицы вне frontend-объёма. Применять SQL только в явно разрешённой среде, не удалять данные. Отчёт о тестовых SQL-проверках не заменяет разрешение на общую БД.

## 3. Стек и архитектура

Сохранять три независимых приложения React + JavaScript/JSX + Vite и npm workspaces. Типы проверяются JSDoc/CheckJS: allowJs, checkJs, noEmit, strict. Не переводить код на .ts/.tsx, не добавлять UI-kit, state-management, монорепо-сборщик, новые библиотеки или существенные обновления без согласования. Зависимости, уже предусмотренные проектом, устанавливать можно. Глобально отключать CheckJS ради прохождения проверок нельзя.

Web уже использует FSD; CMS и модерация пока сохраняют прежнюю структуру. Не создавать пустые слои и пакеты. После согласованного переноса соблюдать направление слоёв, изоляцию слайсов, публичные интерфейсы и запрет циклов. Приложения не импортируют внутренний код друг друга. Тесты принадлежат своим модулям и не экспортируются в production API.

### 3.1. Читаемость и форматирование

**Весь редактируемый вручную frontend-код должен быть развёрнутым и понятным. Запрещено писать сжатый, трудно читаемый код ради уменьшения количества строк.** Правило относится к JavaScript/JSX, CSS, тестам, скриптам и конфигурациям всех frontend-приложений. Минифицированные результаты сборки, автоматически сгенерированные файлы и сторонние зависимости вручную не форматируются.

- Автоматическое форматирование выполняет локальный Prettier по единой конфигурации [.prettierrc.json](.prettierrc.json). Она действует на web, cms, moderation, общие каталоги и будущие frontend-пакеты. Другие конфигурации Prettier без отдельной необходимости не создавать.
- Стандарт: `tabWidth: 2`, `useTabs: false`, `printWidth: 80`, `singleQuote: true`, `jsxSingleQuote: false`, `semi: true`, `trailingComma: "all"`, `singleAttributePerLine: true`, `endOfLine: "lf"`. Использовать два пробела, без символов табуляции для отступов. Ширина 80 является ориентиром форматтера, а не запретом длинных неделимых строк.
- Настройки редактора находятся в [.editorconfig](.editorconfig) и [.vscode/settings.json](.vscode/settings.json). Не менять пользовательские настройки или настройки backend ради frontend-форматирования. Условия применения настроек VS Code описаны в README.
- ESLint отвечает за качество кода: обязательны `curly: ["error", "all"]` и `no-nested-ternary: "error"`. `eslint-config-prettier` отключает конфликтующие правила оформления; `curly: all` явно включён после него. Не запускать Prettier как ESLint-плагин и не подключать полный Airbnb preset.
- Использовать `npm run format:check` для проверки без записи. `npm run format` форматирует весь frontend и запускается только при согласованном массовом изменении; для отдельных изменённых файлов использовать локальный CLI Prettier с явным списком путей. Перечень исключений находится в [.prettierignore](.prettierignore).
- Сохранять пустые строки между самостоятельными логическими блоками. Автоматические переносы и пробелы определяет Prettier; не вводить несовместимые ручные правила и постоянные `prettier-ignore` для обхода стандарта.
- В CSS каждое свойство писать на отдельной строке, каждый селектор в списке переносить на отдельную строку. Тела правил и медиазапросов оформлять многострочно с отступами; между правилами оставлять пустую строку.
- В JavaScript не объединять несколько инструкций в одну строку. Условия, циклы, обработчики и блоки функций раскрывать на несколько строк; у `if`, `else` и циклов использовать фигурные скобки даже для одного действия.
- Длинные объекты, массивы, вызовы функций и выражения переносить по смысловым частям. Не использовать вложенные тернарные операторы и плотные цепочки условий; сложную проверку разбивать на именованные промежуточные значения или небольшие функции.
- В JSX не собирать несколько самостоятельных элементов в одну строку. При нескольких атрибутах или длинных значениях раскрывать тег многострочно, вложенные элементы оформлять с отступами. Обработчики с несколькими действиями выносить в именованные функции.
- Использовать содержательные имена переменных, функций и компонентов. Комментарии объясняют причины и неочевидные ограничения, но не заменяют понятную структуру кода.
- Перед завершением просматривать изменённые участки на читаемость. Прохождение линтера не отменяет эти требования; нечитаемые существующие примеры не являются образцом для нового кода. Посторонние файлы не переформатировать без поручения.

## 4. Данные, безопасность и содержимое

- Браузер получает данные только через API, не подключается к SQL Server. DTO, endpoint, роли и SQL-столбцы не выдумывать.
- Обычные ответы используют JSON; загрузка файлов формами использует multipart/form-data. Список новостей использует coverUrl и отдельные img-запросы, без multipart/mixed.
- Сессия определяется серверной cookie. Защищённый UI не отображать до проверки доступа API. Клиентское скрытие кнопок не является контролем прав; cookie, CORS и CSRF сверять с контрактом.
- Не включать секреты в VITE_*, исходники и Git. Сетевые ошибки отображать безопасно, значения форм сохранять, успех показывать после подтверждения API.
- MSW разрешён для согласованного участка новостей в явно включённом DEV-режиме и тестах. Материалы вымышленные, индикатор явный. Production не включает worker/обработчики. Неизвестные запросы выбранного API блокируются; ресурсы приложения не блокируются. Новые mock-операции требуют согласованного объёма.
- Подписки, списки подписчиков, маркетинговые рассылки и флаг «Оповестить» исключены. Служебное подтверждение email и восстановление доступа рассматриваются по актуальному контракту отдельно от рассылок.
- Не придумывать лор, тексты игры и новые механики. Продуктовые требования и их расхождения сохранены в отдельном документе; архитектурный перенос их не разрешает.

## 5. Проверки и документация

Все npm-команды выполнять из Frontend. Для изменений кода запускать доступные применимые быстрые проверки: ESLint, CheckJS, Vitest/React Testing Library и сборку затронутой области. Полный npm run check проверяет все приложения. Для документации проверять относительные ссылки, отсутствие ссылок на удалённые файлы и соответствие команд конфигурации. Не писать тесты, проверяющие лишь наличие каталогов.

Длительные/тяжёлые Playwright, нагрузочные проверки, запуск полноценной локальной системы и изменения БД требуют согласования, если прямо не включены в задачу. SQL проверять только в разрешённой тестовой среде. Моки не подтверждают серверную интеграцию; автоматические проверки не подтверждают визуальную приёмку.

При изменении запуска и возможностей обновлять README. Архитектурные правила, требования и ADR вести в соответствующих документах без дублирования DTO. Дополнительную документацию создавать по запросу; локальные README нужны только сложным подсистемам в согласованном объёме. Отчёт должен различать выполненные проверки, исторические результаты и непроверенные области.

## 6. Git и приоритет правил

Не уничтожать пользовательские изменения. Локальные коммиты в объёме задачи разрешены. Push, pull, fetch и другие операции с удалёнными репозиториями требуют отдельного разрешения. Не применять reset --hard, широкое clean и переписывание истории без прямого согласования. Убирать только собственные временные файлы.

Приоритет: актуальные прямые указания пользователя и запрет изменения backend; действующие требования с более новыми явно принятыми решениями; архитектура; эти инструкции; локальные соглашения кода. При существенном конфликте остановить спорную часть и уточнить, не подменять требования предположением.
