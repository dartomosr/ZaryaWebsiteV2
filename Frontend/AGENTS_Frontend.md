# AGENTS_Frontend.md - правила работы над вебсайтом «ЗАРЯ»

Инструкции для программирующих агентов, работающих в **едином репозитории** проекта «ЗАРЯ». Сначала прочитать [README проекта](../README.md), [README frontend](README_Frontend.md), [архитектуру frontend](ARCHITECTURE_Frontend.md), при интеграции [BACKEND_INTEGRATION.md](../Backend/BACKEND_INTEGRATION.md) и относящиеся к задаче файлы. Важные правила ниже имеют приоритет над удобством реализации.

## 1. Главный запрет: серверная часть только для чтения

**Не изменять серверную часть ни при каких обычных задачах frontend.** Это включает:

- исходники ASP.NET Core, контроллеры, сервисы, DTO, модели и конфигурацию;
- Entity Framework Core, миграции и модель данных backend;
- настройки запуска, deployment и конфигурацию backend;
- SQL-объекты `Users`, `Comments`, `NewsReactions` и другие таблицы не из закреплённого объёма;
- любые изменения, которые косвенно перенастраивают backend через инфраструктурные файлы.

**Разрешено:** читать серверный код и документацию API, чтобы выяснять фактические контракты. Если для frontend необходима серверная доработка, **остановиться в затронутой части**, сообщить пользователю конкретную проблему и варианты, предложить запрос ответственному разработчику backend. Самостоятельные исправления backend и обходные вмешательства запрещены.

Никакое описание задачи в общих словах («почини интеграцию», «сделай сайт рабочим») не отменяет этот запрет. Серверные файлы могут менять только их ответственные разработчики вне данного агентского объёма.

Серверная зона находится в `Backend/`. Frontend-код, инструменты, тесты и будущие согласованные SQL-скрипты `News`/`Updates` находятся в `Frontend/`. Все npm-команды выполнять из `Frontend/`. Пути `Frontend/` и `Backend/` в этом документе указаны относительно корня репозитория.

## 2. Разрешённая зона изменений

- Frontend трёх отдельных React-приложений: `Frontend/apps/web`, `Frontend/apps/cms`, `Frontend/apps/moderation` (или их фактические каталоги после изучения репозитория).
- Собственные frontend-тесты, стили, ресурсы, конфигурация сборки, линтинга и проверки JavaScript.
- Отдельные T-SQL-скрипты **только** для таблиц `News` и `Updates` в согласованной директории; **не** миграции EF Core.
- Документы `Frontend/README_Frontend.md`, `Frontend/ARCHITECTURE_Frontend.md`, `Frontend/AGENTS_Frontend.md` и корневой `README.md`, когда изменения соответствуют задаче. `Backend/BACKEND_INTEGRATION.md` можно изменять только при отдельном поручении на документацию интеграции; это не разрешение менять остальные серверные файлы.

Перед созданием или изменением схемы `News`/`Updates` изучить известные API/EF-модели **в режиме чтения**, согласовать с владельцем backend имена, типы, FK, индексы, совместимость и процедуру применения. Не применять DDL к общей или неизвестной БД без явного разрешения. Не удалять пользовательские данные. Демо-данные - только в разрешённой тестовой среде.

## 3. Неподлежащие восстановлению функции

В текущей версии **полностью исключены**:

- подписки и списки подписчиков;
- формы/переключатели подписки;
- почтовый сервис, отправка уведомлений и отписка;
- флаг «Оповестить» в CMS.

Не добавлять их «на будущее», не создавать заглушки, поля БД, компоненты UI или обходные маршруты без нового согласования. Поле email для учётной записи **остаётся**.

## 4. Язык, стек, структура

- Общение с пользователем, комментарии в важных документах и описания решений - преимущественно **на русском**; имена сущностей и идентификаторы кода остаются понятными и стабильными.
- Три **отдельных** frontend-приложения: React + **JavaScript/JSX** + Vite.
- Проверка типов без обязательной миграции на TypeScript: `checkJs`/`allowJs`, `noEmit`, JSDoc там, где типы недостаточно очевидны, в особенности в DTO, формах и функциях API.
- ESLint для статического анализа, Vitest + React Testing Library для быстрых проверок, Playwright для отдельных браузерных и визуальных сценариев.
- Не переводить новый frontend-код на `.ts/.tsx`, не добавлять масштабный UI-kit, state-management библиотеку, монорепо-сборщик или иные зависимости **без явного обоснования и согласования ключевого решения**.
- Избегать преждевременной абстракции и копирования бизнес-правил между компонентами. Повторяющиеся подходы объединять только при реальной необходимости и с согласованием существенного рефакторинга.

## 5. Технические границы frontend

- Данные браузера - **только через ASP.NET Core API**, не через прямое подключение к SQL Server.
- API-формат: JSON; изображения передавать `multipart/form-data`.
- Сессия определяется серверной cookie. Проверка `Admin`/`Moderator` должна выполняться через API **до отображения** защищённого интерфейса.
- Не считать скрытую кнопку или клиентский route guard достаточным контролем прав.
- Не выдумывать URL endpoint, имена полей JSON, роли сверх ТЗ, SQL-столбцы и поведение backend. Если данных нет, зафиксировать неопределённость и согласовать контракт.
- Не включать секреты в `VITE_*`, код frontend и Git.
- Не внедрять фиктивную авторизацию, успешные ответы или фронтенд-обходы вместо серверной доработки. MSW разрешён в явно включённом режиме разработки и в тестах для согласованного участка новостей. Данные вымышленные, индикатор режима явный; обычный запуск не активирует моки, production не включает worker и обработчики. Неизвестные запросы выбранного API блокируются, ресурсы Vite и приложения не блокируются. Новые мок-операции требуют согласованного объёма; моки не заменяют серверный контроль прав.

## 6. Требования к реализации

Сохранять функциональные требования из `ARCHITECTURE_Frontend.md` и исходных учебных документов, кроме согласованного удаления подписок. Особое внимание:

- публичный сайт от 320 px; CMS и модерация от 1024 px;
- сетка карточек: 4 / 3 / 1 на порогах 1440 / 768 px;
- навигация в меню при ширине менее 1024 px;
- главная: максимум 3 последних опубликованных материала каждого типа;
- раскрытие полного описания без API-запроса и смены маршрута;
- реакции только новостей, взаимоисключение и снятие реакции;
- комментарии только при активной сессии; удаление собственного комментария;
- CMS: черновики, публикация, удаление, загрузка JPEG/PNG/WebP <= 5 МБ;
- модерация: явное подтверждение удаления;
- валидация до запроса и ошибки под соответствующими полями;
- сетевые/5xx ошибки без технических деталей, сохранение заполненных форм;
- дата/время публикации устанавливаются backend.

Публичный визуальный язык - тёмная палитра, белый текст, жёлто-оранжевые/фиолетовые акценты и мотивы карт. Не придумывать сюжетные тексты, лор и содержимое игры без предоставленных материалов или согласования.

## 7. Порядок выполнения задачи

1. **Сначала понять задачу.** Изучить релевантный код, README, архитектуру и API. Если задача требует важного выбора, предложить план и получить согласование до реализации.
2. **Проверить границы.** Убедиться, что изменения ограничены frontend, собственными SQL-скриптами и документацией.
3. **Внести минимальные изменения.** Не выполнять рефакторинг сторонних частей без отдельного согласования.
4. **Проверить результат.** Выполнить все доступные **быстрые** проверки, относящиеся к изменённой части: ESLint, CheckJS, Vitest/React Testing Library, сборку при необходимости, простые SQL-проверки только в разрешённой тестовой среде.
5. **Тяжёлые проверки только по разрешению.** Перед длительными/тяжёлыми Playwright, нагрузочными тестами, запуском полноценной локальной системы или изменениями БД запросить согласование, если пользователь явно не поручил их в задаче.
6. **Документировать.** После изменения реализованных возможностей, команд запуска или окружения актуализировать `README_Frontend.md`; при согласованных изменениях структуры актуализировать `ARCHITECTURE_Frontend.md`, HTTP-контракты и их статусы вести в `Backend/BACKEND_INTEGRATION.md` в рамках разрешённой задачи. Не дублировать подробные DTO в README.
7. **Отчитаться.** Кратко указать изменённые файлы, поведение, проведённые проверки, результаты и известные ограничения. Не заявлять, что тесты прошли, если их не запускали.

**Правило блокировки:** если проблема не решается быстро, **немедленно сообщить пользователю** с коротким описанием причины и 1-2 разумными вариантами решения. Не тратить много времени на самостоятельные обходы. Если разработчик backend должен что-либо изменить, это именно такой блокер.

## 8. Git и рабочая гигиена

- Разрешены локальные коммиты по усмотрению агента, если это не противоречит текущей задаче.
- **Не выполнять `git push`, force-push и другие операции изменения удалённого репозитория** без отдельного поручения. Force-push по умолчанию не допускается.
- Не удалять чужие незакоммиченные изменения и не перезаписывать файлы пользователя без необходимости.
- Не совершать разрушительные операции Git (`reset --hard`, широкое `clean`, переписывание истории) без прямого согласования.
- После выполнения убрать собственные временные файлы, лишние артефакты сборки и мусор; не трогать чужие файлы.
- Не фиксировать секреты, ключи и персональные данные в истории Git.

## 9. Актуальные границы известного

Пути трёх приложений, npm-команды и проверки уже существуют; перед работой сверять их с кодом. Предварительный контракт новостей реализован во frontend/MSW, но не подтверждён backend. Открыты реальные API-адреса и остальные DTO, cookie/CORS/CSRF, физические схемы `News`/`Updates`, их совместимость с EF Core и наличие утверждённых материалов игры/PressKit. Подробный реестр находится в [документе интеграции](../Backend/BACKEND_INTEGRATION.md#6-открытые-вопросы).

Одобрение frontend-мока не означает согласования серверного контракта. При существенной неопределённости изучить доступные материалы и запросить решение, не подменяя её догадкой.

## 10. Приоритет инструкций

1. Прямые актуальные указания пользователя и абсолютный запрет менять backend.
2. Исходные задания на практику и техническое задание с утверждёнными изменениями, в том числе без почтового функционала.
3. Согласованная техническая архитектура из `ARCHITECTURE_Frontend.md`.
4. Этот файл как правила ежедневной агентской работы.
5. Локальные соглашения существующего кода, не противоречащие вышеперечисленному.

При противоречии требований, влияющем на функциональность или ответственность, остановиться в спорной части и запросить решение у пользователя.
