# Архитектура Frontend ZaryaWebsite

**Статус:** целевое направление согласовано 18.11.2026. Публичное приложение web переведено на FSD: заново созданы главная и новости. CMS и модерация пока сохраняют прежнюю структуру.

## 1. Назначение и границы

Frontend состоит из трёх независимых React-приложений: публичного сайта `web`, управления контентом `cms` и модерации `moderation`. У каждого собственные точка входа, маршруты и сборка. Приложения используют единый HTTP API и не импортируют исходники друг друга. npm workspaces управляет пакетами в одном репозитории; объединения приложений во время выполнения нет.

Этот документ определяет организацию frontend-кода. [Требования](REQUIREMENTS.md) описывают поведение интерфейсов, [инструкция разработки](../README.md) содержит команды, [OpenAPI](../../ApiContracts/README.md) описывает HTTP-контракты. Архитектура backend, EF Core и SQL Server не меняется.

FSD близок к Clean Architecture разделением ответственности и контролем зависимостей, но не является её полной реализацией.

## 2. Текущая структура

В web используются четыре слоя. Общие данные новостей нужны двум страницам, поэтому выделен entities/news. Пустых widgets и features нет.

```text
apps/web/src/
  main.jsx
  app/
    App.jsx
    styles/global.css
    tests/setup.js
    tests/App.test.jsx
  pages/
    home/
      ui/HomePage.jsx
      tests/HomePage.test.jsx
      index.js
    news/
      ui/NewsPage.jsx
      tests/NewsPage.test.jsx
      index.js
  entities/
    news/
      api/                   # HTTP, DTO и проверка ответа
      model/useNewsFeed.js   # загрузка, отмена, пагинация и дедупликация
      ui/                    # карточка и её стили
      tests/
      index.js
  shared/
    config/                  # API base для клиента и MSW
    ui/site-layout/          # общая шапка, мобильное меню и подвал
```

Главная получает до трёх новостей, список /news загружает страницы по 12 записей. Оба экрана используют сущность новости через её публичный интерфейс. Обработку запросов и проверку DTO страницы не дублируют. Неизвестные пути пока показывают главную, отдельного 404 и роутер-библиотеки нет. Навигация выполняется обычными ссылками.

CMS и модерация пока содержат прежние app, pages, styles и test. Они показывают закрытые оболочки без проверки сессии. Их перенос не входил в пересоздание публичных страниц. Общих workspace-пакетов и глобального хранилища нет.

Слои и сегменты добавляются по фактической необходимости. Выделение entities/news связано с повторным использованием на двух страницах; оно не требует аналогичного дробления каждой будущей функции.

## 3. Слои и зависимости

Разрешённое направление зависимостей:

`app → pages → widgets → features → entities → shared`

Слой может обращаться к любому нижележащему слою, пропускать промежуточные слои разрешено.

| Слой | Ответственность |
| --- | --- |
| `app` | Инициализация, маршруты, общие провайдеры и композиция приложения |
| `pages` | Экраны; их UI, загрузка, формы и логика, пока они локальны экрану |
| `widgets` | Самостоятельные крупные блоки интерфейса, объединяющие нижние слои |
| `features` | Выделенные значимые пользовательские сценарии, например отправка комментария |
| `entities` | Повторно используемые предметные понятия, например новость или пользователь |
| `shared` | Общие UI-элементы и инфраструктура без бизнес-правил приложения |

Правила:

1. Нижние слои не импортируют верхние. Слайсы одного слоя не импортируют друг друга даже через публичные интерфейсы.
2. Внешние потребители используют публичный интерфейс слайса `index.js`. Экспортируются только необходимые элементы, без массового `export *`.
3. Внутри слайса используются прямые относительные импорты, без обращения к собственному корневому `index.js`.
4. Для `shared` публичные точки входа выделяются по назначению, например для кнопки или библиотеки дат. Единый barrel всего `shared` не нужен.
5. `app` и `shared` не подчиняются изоляции соседних слайсов, поскольку слайсов в них нет. Циклические зависимости запрещены во всех слоях.
6. Специальные cross-import API сущностей (`@x`) не вводятся по умолчанию. Необходимость исключения обсуждается отдельно и фиксируется вместе с причиной.
7. Не каждое действие является feature. Локальная форма и её валидация могут оставаться на странице. Выделение слоя должно решать конкретную задачу композиции, повторного использования или изоляции ответственности.

В текущем web страницы home и news используют общий entities/news. Самостоятельный widget ленты не нужен: композиция остаётся на страницах. При расхождении сценариев загрузки их модели можно разделить, сохранив общие DTO и карточку.

Основание: [слои FSD](https://feature-sliced.design/docs/reference/layers), [слайсы и сегменты](https://feature-sliced.design/docs/reference/slices-segments), [публичные интерфейсы](https://feature-sliced.design/docs/reference/public-api).

## 4. Общие пакеты

Код выносится в `Frontend/packages` при подтверждённой потребности нескольких приложений. Потенциальные пакеты: `ui` для общих элементов оформления, `api-client` для HTTP-транспорта, отдельный пакет контрактов для действительно одинаковых DTO и валидаторов. Пакет `utils` без определённых границ ответственности не создаётся.

Приложение импортирует пакет через его публичные exports. Пакет не зависит от приложений. Его тесты находятся внутри пакета; зависимости объявляются явно. При появлении пакетов нужно расширить текущий workspace-шаблон `apps/*`, подключить их к проверке типов, тестам и необходимой сборке. Техническую схему сборки выбирают при создании первого пакета.

Общий пакет не является обходом правил FSD: перенос туда бизнес-логики с целью разрешить запрещённый импорт недопустим. Приложения могут различаться по UI и моделям, даже если используют один API.

## 5. Данные и состояние

Поток данных: UI вызывает модель или API-функцию; API-функция выполняет HTTP-запрос, проверяет ответ и при необходимости преобразует DTO. MSW подменяет сеть, а не код компонентов. Production-компоненты не импортируют фикстуры.

Разделяются следующие обязанности:

- HTTP-транспорт: адрес, заголовки, отмена запросов и технические ошибки.
- API предметной области: конкретные операции и преобразования ответа.
- DTO и runtime-валидация: проверка данных на границе сети. JSDoc не заменяет проверку JSON во время выполнения.
- Модель UI: пагинация, состояние формы, выбор объектов и состояния загрузки.

API-код может находиться в сегменте `api` страницы, feature или entity в зависимости от владельца и использования. Общие механизмы находятся в `shared/api`. Не требуется одновременно создавать все эти уровни.

OpenAPI является источником HTTP-схем. Не создаётся второй независимый реестр контрактов в архитектурной документации. Статус `proposed` не подтверждает реализацию сервера. Совпадение форматов публичного чтения и CMS не предполагается автоматически. Генерация клиента и валидаторов остаётся открытым инструментальным решением.

Локальное состояние хранится рядом с владельцем. Серверные данные, состояние формы и глобальная сессия имеют разные обязанности и не объединяются в общее хранилище автоматически. Сессия определяется API; роль клиента не заменяет серверный контроль прав.

## 6. Мировая Машина

Мировая Машина рассматривается как автономная подсистема с внутренней архитектурой и ограниченным публичным интерфейсом. Области ответственности: географическая карта, системная сеть, камера и масштаб, переключение пространств, тематическая навигация, анимации и интерактивные объекты.

Если подсистема целиком принадлежит одному экрану, начальное размещение возможно в слайсе страницы. Если это самостоятельная встраиваемая сцена, возможно размещение в widget. Окончательная граница выбирается после изучения реализации и сценариев использования. Дополнительный верхнеуровневый FSD-слой `world-machine` не вводится.

Внутри подсистемы можно выделять камеру, навигацию, переходы и представление. Каждая анимация или операция камеры не становится отдельной feature. Независимое от React ядро выделяется только при наличии реальной вычислительной границы. Зависимости слайса соблюдают правила выбранного слоя; автономность не разрешает запрещённые импорты.

Тесты камеры, навигации и переходов принадлежат подсистеме. Для сложного внутреннего устройства создаётся локальный README. Выбор движка, публичных параметров и событий пока открыт.

## 7. Тестирование и контроль архитектуры

Unit-, компонентные и локальные интеграционные тесты находятся в `tests/` своего слайса. Один небольшой тест допускается рядом с реализацией. Внутренние тесты могут обращаться к внутренним функциям своего слайса; наружу тестовые файлы не экспортируются.

Интеграционные тесты нескольких слайсов размещаются на уровне приложения, например `src/app/tests`. Сквозные сценарии остаются в `Frontend/tests/e2e`. Тесты пакетов принадлежат пакетам. Контрактные проверки остаются в `ApiContracts`.

Общая настройка Vitest и MSW не копируется в слайсы. При переносах сохраняются сброс обработчиков, очистка DOM, отмена запросов и изоляция сценариев. Моки включаются явно только в разработке и тестах; проверка production-сборки сохраняется.

Тесты проверяют поведение, а архитектурные проверки проверяют граф импортов, а не существование каталогов. После миграции планируется автоматизировать запрет восходящих импортов, обхода публичных API, связей соседних слайсов, циклов и импортов между приложениями. Текущий ESLint этих гарантий ещё не даёт. Выбор полноценного анализатора согласуется при внедрении; новые зависимости сейчас не добавляются.

## 8. Стек и отложенные решения

Сохраняются React, JavaScript/JSX, Vite и npm workspaces. Типы проверяются через JSDoc/CheckJS с `strict`, без миграции на TypeScript. Используются ESLint, Vitest, React Testing Library, MSW и Playwright. Backend остаётся на существующем стеке ASP.NET Core/C#, с целевыми EF Core и Microsoft SQL Server. OpenAPI 3.0.3 и Python/JSON Schema обслуживают контракты отдельно от frontend-сборки.

Роутер, библиотека серверного состояния, глобальное хранилище, движок карты, генератор API-клиента и анализатор FSD выбираются при конкретной потребности. Отсутствие выбора сейчас не разрешает вводить их без обсуждения. Текущая ручная маршрутизация не объявляется долгосрочным решением.

## 9. Документация и миграция

Этот документ является единственным основным описанием frontend-архитектуры. Запуск описывается в frontend README, поведение интерфейсов в требованиях, ограничения действий агентов в `Frontend/AGENTS.md`. Локальные README создаются только для сложных подсистем.

Значимые принятые решения фиксируются ADR с контекстом и последствиями. [ADR 001](decisions/001-use-fsd.md) фиксирует выбор FSD. Общие пакеты и инструменты получат отдельные ADR, когда будут конкретные решения.

[План миграции](MIGRATION.md) отделён от архитектурных правил. Обновление документации не является разрешением на перенос кода, изменение API, backend или функциональных требований.

### Жизненный цикл плана миграции

MIGRATION.md является временным рабочим файлом и удаляется после завершения базового переноса на FSD. Перед удалением сюда переносятся фактическая структура, сохраняемые ограничения и открытые архитектурные решения; команды обновляются в frontend README, значимые решения фиксируются ADR, требования остаются в REQUIREMENTS.md. Ссылки на план удаляются из всех документов. Постоянная документация должна быть самодостаточной без плана миграции.
