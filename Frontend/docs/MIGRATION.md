# План перехода frontend на FSD

**Статус:** временный рабочий план базового переноса кода на FSD. Публичное web-приложение пересоздано на FSD. Перенос CMS и модерации, а также автоматический контроль границ ещё не выполнены. План сохраняется до завершения базового перехода.

## 1. Исходное состояние

| Область | Сейчас | Последствие для перехода |
| --- | --- | --- |
| `web` | Главная, список новостей, локальное состояние в NewsPage, отдельный API-код | Основной участок переносов; сохраняются UI и HTTP-поведение |
| `cms`, `moderation` | App и страница недоступности, собственные тесты | Достаточно слайса страницы; feature и entity пока не нужны |
| Тесты | Рядом с API, страницами и App; setup в `src/test` | Локальные тесты переезжают вместе с владельцами |
| MSW | Центральный `Frontend/mocks`, импортируемый web и тестовой средой | Первоначально остаётся на месте |
| Пакеты | Workspace-шаблон только `apps/*`, общих пакетов нет | Выделение пакетов не входит в первый перенос |
| Стили | Глобальный файл каждого приложения | Первоначально переносится как глобальная настройка app без переработки селекторов |

Текущий код лишь частично соответствует FSD: есть app и страницы, но нет слайсов страниц, публичных интерфейсов и автоматического контроля границ. Повторение оболочек CMS и модерации недостаточно для общего UI-пакета. Настройка API-origin является кандидатом для локального `shared/config`; общий пакет транспорта имеет смысл после появления второго потребителя.

## 2. Минимальная целевая структура первого этапа

Для web: `app`, `pages/home`, `pages/news`, необходимые `shared/config` и `shared/api`. Код запроса, DTO и проверки списка сначала принадлежит `pages/news/api`; пагинация и загрузка при необходимости выделяются в `pages/news/model`. Тесты списка находятся в `pages/news/tests`, тесты композиции приложения в `app/tests`. Публичные интерфейсы страниц экспортируют только компоненты страниц.

Для CMS и модерации: `app`, `pages/access-unavailable`, без пустых общих и предметных слоёв. Главная точка входа `src/main.jsx` сохраняется. Не создаются заранее widgets, entities, features или packages.

## 3. Последовательность

1. Зафиксировать исходный `git status` и выполнить `npm run check` из Frontend. Имеющиеся ошибки отделить от последствий миграции. Перенос не начинать без понятного исходного результата.
2. Перенести страницы web в слайсы с публичными интерфейсами. API-логику переместить без изменения проверки DTO, адресов и обработки ошибок. Затем выделить модель страницы, только если это упрощает чтение, отдельным проверяемым шагом.
3. Перенести соответствующие тесты. Исправить импорты, Vitest setupFiles, включения CheckJS, пути к MSW, а при введении alias синхронно настроить Vite и jsconfig. Alias не обязателен для самого переноса.
4. Перенести оболочки CMS и модерации. Сохранить закрытый интерфейс и тексты. Не добавлять фиктивную проверку прав.
5. Перенести глобальные стили и настройку тестовой среды в сегменты app с обновлением всех путей. Центральные моки и E2E оставить на месте.
6. Подключить согласованный контроль архитектурных импортов. Выбор нового инструмента согласовать отдельно; не заменять анализ графа тестом существования папок.
7. Повторить быстрые проверки и проверить diff. Обновить фактическую структуру в документации. Проверить браузерные сценарии по отдельному согласованию, если запуск не включён в задачу миграции.

Каждый шаг должен оставлять проект проверяемым. Не создавать второй параллельный API-клиент или долгосрочные совместимые обёртки по старым путям. Откат выполняется отменой только собственных изменений этапа, без сброса пользовательских правок.

## 4. Что сохраняется

- Маршрут `/news`, текущая главная и закрытые оболочки; выбор роутера в миграцию не входит.
- JSON-массив новостей, поле `coverUrl`, проверка ответа и разрешение URL обложки относительно origin API.
- Размер страницы, отмена запросов, защита от повторной загрузки, удаление дубликатов ID, сохранение карточек и повтор той же страницы после ошибки.
- Явный mock-режим, сценарии MSW, изоляция тестов и проверка production на mock-маркеры.
- Текущие порты, команды, переменные окружения, JSDoc/CheckJS и отсутствие новых зависимостей без согласования.

## 5. Оценка и риски

Объём переноса текущего каркаса небольшой; точный срок определяется после исходных проверок. Большая часть изменений связана с путями, а не с бизнес-логикой. Выделение общих пакетов, новая авторизация и реализация Мировой Машины не включаются в эту оценку.

| Риск | Проверка |
| --- | --- |
| Ошибочные пути и потерянные тесты | CheckJS, Vitest; сопоставление состава сценариев до и после |
| Циклы через index.js | Проверка импортов; внутренние модули не используют собственный barrel |
| Нарушение setup MSW | Тесты сетевых ошибок, сброса обработчиков и отмены |
| Моки в production | Обычная сборка и отдельная сборка web с mock-mode, затем verify-web-build |
| Изменение UI или маршрутов | Сопоставление поведения; браузерная проверка отдельно |
| Конфликт с API | Сохранение существующего адаптера; интеграция с сервером является отдельной задачей |

## 6. Критерии завершения

Быстрые lint, CheckJS, unit/component-тесты и сборки проходят; сохранены прежние сценарии и проверки production. Импорты соответствуют целевым границам, старые пути больше не используются. Заявления о визуальной и серверной проверке делаются только при фактическом выполнении. Документация отражает перенесённый код и явно отмечает оставшиеся ограничения.

## 7. Удаление временного плана

После завершения базового переноса и проверки критериев раздела 6 этот файл удаляется. До удаления необходимо:

1. Перенести фактическую структуру, постоянные правила зависимостей, размещение тестов и оставшиеся архитектурные ограничения в [ARCHITECTURE.md](ARCHITECTURE.md).
2. Обновить команды и инструкции окружения в [README](../README.md), обязательные правила действий в [AGENTS.md](../AGENTS.md), а значимые принятые решения и их последствия в ADR. Продуктовые ограничения сохраняются в [REQUIREMENTS.md](REQUIREMENTS.md).
3. Сохранить незавершённые вопросы в разделе открытых решений архитектуры. Зафиксировать выполненные проверки и ограничения в итоговом отчёте задачи; не выдавать исторические результаты за текущие гарантии.
4. Удалить ссылки на этот временный план из README, AGENTS, архитектуры, ADR и корневой навигации. Проверить ссылки и убедиться, что постоянные документы понятны без MIGRATION.md.

Условия завершения базового переноса не расширяются до реализации всех будущих функций сайта. История промежуточных шагов остаётся в Git и не требует отдельного постоянного документа.

## 8. Выполненный участок web

По отдельному поручению пользователя прежние страницы заменены новыми главной и новостями. Общие API, карточка и модель загрузки выделены в entities/news, поскольку используются двумя страницами. Страницы, конфигурация API и общая оболочка имеют публичные интерфейсы; тесты и глобальные стили перенесены к владельцам. Пути MSW обновлены. Выбор нового роутера, пакеты и перенос других приложений не выполнялись.

Фактическая структура и правила уже описаны в ARCHITECTURE.md, пользовательское поведение в frontend README. Проверены ESLint, CheckJS, 44 теста, сборки трёх приложений и отсутствие mock-маркеров в production web. В браузере с MSW проверены меню, переходы, подгрузка и ширины 320/768/1024/1440 px. Эти результаты относятся к данному этапу, а не к будущим изменениям или настоящему API.
