# ADR 001. Feature-Sliced Design для frontend

**Дата:** 18.11.2026.

**Статус:** принято как целевое архитектурное направление; перенос кода не выполнен.

## Контекст

Три независимых React-приложения объединены npm workspaces. Рабочий участок публичного приложения содержит страницу новостей и API-адаптер. При расширении требуются границы функциональности, правила зависимостей и локальное владение тестами. Текущая группировка по страницам и API не устанавливает эти границы для будущих функций.

## Решение

Использовать FSD отдельно внутри `web`, `cms` и `moderation`. Начинать с минимально необходимых слоёв, соблюдать направление зависимостей, изоляцию слайсов и публичные интерфейсы. Общие пакеты выделять при фактическом повторном использовании. Существующий стек сохраняется. Мировую Машину рассматривать как автономную подсистему в рамках выбранного FSD-слоя.

Подробные правила находятся в [архитектуре](../ARCHITECTURE.md). Последовательность перехода ведётся во временном плане; после завершения базового переноса план удаляется, а постоянные решения сохраняются в архитектуре и ADR.

## Альтернативы

Сохранение плоских `pages` и `api` проще для нынешнего каркаса, но не задаёт будущие границы. Произвольные функциональные модули уменьшают количество соглашений, однако требуют собственных правил зависимостей. Выбран FSD с минимальным набором слоёв и без обязательного дробления каждой операции.

## Последствия

Появляются единые правила размещения и использования кода. Потребуются перенос импортов и тестов, актуализация конфигурации и последующий автоматический контроль зависимостей. Возникает стоимость соблюдения публичных интерфейсов; её ограничивают созданием только нужных слоёв. Решение не меняет backend, HTTP-контракты и поведение приложений и не выбирает новые библиотеки.
