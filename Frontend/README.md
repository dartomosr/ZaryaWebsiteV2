# Frontend вебсайта «ЗАРЯ»

Инструкция по локальной разработке трёх независимых React-приложений. Текущее состояние проекта описано в [корневом README](../README.md), организация кода в [архитектуре](docs/ARCHITECTURE.md), поведение интерфейсов в [требованиях](docs/REQUIREMENTS.md), HTTP-контракты в [OpenAPI](../ApiContracts/README.md). Правила выполнения изменений находятся в [инструкциях агентов](AGENTS.md).

## Окружение и установка

Нужны Git, Node.js **24.x**, npm **>=11**. Линия Node указана в `.nvmrc`, зависимости зафиксированы в `package.json` и `package-lock.json`. Все npm-команды ниже выполняются из `Frontend`.

```powershell
cd Frontend
npm ci
```

Для текущего участка с MSW сервер и БД не нужны. Обычный режим публичного сайта проксирует `/api/*` на backend `http://localhost:5257`; перед запуском `dev:web` или предпросмотра сборки сервер должен быть доступен на этом адресе. Это локальная настройка разработки; адрес реального развёртывания задаётся отдельно.

## Запуск приложений

Каждое приложение запускается в своём терминале. Порты фиксированы: занятый порт вызывает ошибку, автоматического переключения нет. Серверы доступны только на `127.0.0.1`.

| Команда | Приложение | Адрес |
| --- | --- | --- |
| `npm run dev:web` | Публичный сайт, обычный API-режим | [5173](http://127.0.0.1:5173) |
| `npm run dev:web:mock` | Публичный сайт с MSW | [Новости](http://127.0.0.1:5173/news) |
| `npm run dev:cms` | Закрытая оболочка CMS | [5174](http://127.0.0.1:5174) |
| `npm run dev:moderation` | Закрытая оболочка модерации | [5175](http://127.0.0.1:5175) |

Два режима публичного сайта одновременно используют один порт, запускать нужно один из них. CMS и модерация пока не имеют mock-команд, авторизации и рабочих защищённых интерфейсов.

Обычный режим и production-предпросмотр передают запросы `/api/*` на `http://localhost:5257`. Запустите backend отдельно и затем `npm run dev:web` (или команду предпросмотра сборки); браузер открывает frontend на `127.0.0.1:5173` или `127.0.0.1:6173`, а Vite проксирует API-запросы. Если backend ещё не запущен, запросы новостей завершатся ошибкой. Для работы без backend используйте `npm run dev:web:mock`.

Список использует актуальный [OpenAPI](../ApiContracts/openapi.yaml): `GET /api/news?page=1&pageSize=12` возвращает JSON-массив. API-клиент проверяет DTO и разрешает относительный `coverUrl` относительно origin API; обычные lazy `<img>` загружают изображения отдельно. Короткая или пустая страница завершает подгрузку, полная позволяет запросить следующую по клику. Ошибка подгрузки сохраняет карточки и допускает повтор той же страницы; повторные ID не добавляются.

Реальная интеграция с backend не подтверждена. Клиент ожидает `coverUrl`; проверка наличия и совместимости серверных операций выполняется отдельно. Старое поле изображений клиент не поддерживает.

## Переменные окружения

Образец: [apps/web/.env.example](apps/web/.env.example). Для локальных значений можно скопировать его в `apps/web/.env.local`, который исключён из Git. После изменения окружения перезапустите Vite.

| Переменная | Значение и действие |
| --- | --- |
| `VITE_API_BASE_URL` | API base, включает префикс; по умолчанию `/api/`, который Vite направляет на `http://localhost:5257`. Для другого окружения задаётся свой base с префиксом; настройка Vite proxy также должна соответствовать серверу |
| `VITE_MOCK_SCENARIO` | Сценарий MSW, по умолчанию `default`; не влияет на обычный API-режим |
| `VITE_ENABLE_MOCKS` | Явный флаг включения. `true` задан в отслеживаемом `apps/web/.env.mock`, используемом `vite --mode mock` |

Моки запускаются только при `import.meta.env.DEV` и `VITE_ENABLE_MOCKS === 'true'`. Не задавайте этот флаг в `.env.local` или общем окружении для обычного API-запуска. Production не включает моки даже при `--mode mock`. Секреты в `VITE_*` запрещены: значения доступны браузеру.

## MSW и сценарии

MSW 3.0.3 подключён через официальный `msw/vite` при Vite 8.3.5. Worker обслуживается плагином при разработке, файла в `public` нет. React запускается после готовности перехвата запросов. При включённых моках виден индикатор «Тестовые данные».

| Сценарий | Поведение |
| --- | --- |
| `default` | 26 вымышленных новостей, при размере 12 получается три страницы |
| `empty` | Пустой список |
| `slow` | Задержка ответа 1500 мс |
| `error` | HTTP 503 |
| `network-error` | Ошибка соединения |
| `next-page-error` | Первая страница успешна, последующие возвращают 503 |

В PowerShell сценарий можно выбрать на время работы терминала:

```powershell
$env:VITE_MOCK_SCENARIO = "empty"
npm run dev:web:mock
# После остановки Vite (Ctrl+C):
Remove-Item Env:VITE_MOCK_SCENARIO
```

Неизвестное имя сценария останавливает mock-запуск. Обработчики и данные централизованы в `mocks`; материалы вымышлены и не являются текстом или лором игры. Состояние не сохраняется между перезагрузками. Авторизация, регистрация, CMS и модерация не моделируются.

Неизвестные HTTP-запросы внутри выбранного API-origin и API-префикса блокируются с явной ошибкой. Остальные ресурсы, в том числе Vite и изображения, пропускаются. Эта политика не является общим запретом любых внешних запросов.

## Проверки и сборка

| Команда | Назначение |
| --- | --- |
| `npm run lint` | ESLint |
| `npm run format` | Запись форматирования Prettier во всём frontend; только для согласованного массового изменения |
| `npm run format:check` | Проверка форматирования без записи |
| `npm run typecheck` | Строгий CheckJS/JSDoc во всех приложениях |
| `npm run test:unit` | Vitest и React Testing Library во всех приложениях |
| `npm run build` | Сборка трёх приложений |
| `npm run check` | Последовательно format:check, lint, typecheck, test:unit и build; останавливается при первой ошибке |
| `npm run test:e2e` | Отдельный запуск Playwright |

Vitest публичного приложения явно запускает Node-интеграцию MSW; после каждого теста сбрасываются обработчики, DOM и путь страницы, после набора тестов сервер перехвата закрывается. Тестовый base зафиксирован как `http://localhost:3000/api/`; настройка другого `VITE_API_BASE_URL` для тестов может потребовать отдельного согласованного изменения тестового окружения.

## Единый стиль форматирования

Prettier является единственным автоматическим форматтером. Версии Prettier и eslint-config-prettier зафиксированы точно в package.json и lock-файле. Общая [.prettierrc.json](.prettierrc.json) применяется ко всем трём приложениям, мокам, скриптам, тестам, документации и будущим frontend-пакетам. ESLint проверяет качество кода, включая обязательные фигурные скобки и запрет вложенных тернарных операторов. Полный Airbnb preset и eslint-plugin-prettier не используются.

Стандарт: два пробела без табуляции, ориентир ширины 80, одинарные кавычки JS и двойные JSX, точки с запятой, trailingComma: all, отдельные строки для JSX-атрибутов и окончания строк LF. Prettier может оставлять неделимые строки длиннее 80 символов. Понятные имена и простота логики остаются ответственностью разработчика.

Сборки, зависимости, coverage, браузерные отчёты, генерируемый MSW worker, lock-файлы и локальное окружение исключены через [.prettierignore](.prettierignore). Собственные новые генерируемые каталоги нужно добавлять в исключения при их появлении. Команды выполняются из Frontend и не затрагивают Backend, ApiContracts и Storage.

Для нескольких явно выбранных файлов:

```powershell
npm exec -- prettier apps/web/src/shared/ui/site-layout/SiteLayout.jsx --check
npm exec -- prettier apps/web/src/shared/ui/site-layout/SiteLayout.jsx --write
```

Второй вариант записывает изменения; при первоначальной настройке стандарта он не запускался для существующих исходников. Не применять eslint --fix ко всему frontend в обход согласования массовых изменений.

### Настройки редактора

[.editorconfig](.editorconfig) задаёт UTF-8, LF и отступы пробелами для редакторов с поддержкой EditorConfig. Завершающие пробелы Markdown автоматически не удаляются, поскольку могут обозначать перенос строки.

[.vscode/settings.json](.vscode/settings.json) явно задаёт размер Tab 2, вставку пробелов и отключает определение отступов по содержимому. Эти настройки применяются, если Frontend открыт как отдельная папка workspace или добавлен отдельной папкой в multi-root workspace. При открытии только корня репозитория вложенные настройки VS Code не подхватываются. Для применения .editorconfig в таком режиме используйте поддержку EditorConfig, например расширение EditorConfig for VS Code; Prettier при ручном форматировании сам находит frontend-конфигурацию.

Для выбранного форматтера в VS Code требуется расширение Prettier - Code formatter. Расширения и пользовательские настройки автоматически не устанавливаются и не меняются. Автоформатирование при сохранении этой настройкой не включается: существующий код не должен массово изменяться во время внедрения стандарта.

### Переход существующего кода

Стандарт настроен без массового форматирования. Старые файлы пока могут не проходить format:check и новые правила ESLint; это не конфликт конфигураций. Общий check в таком состоянии завершится до последующих проверок. До отдельного этапа приведения к стилю typecheck, test:unit и build можно запускать независимо. Масштаб и результаты первоначальной проверки приведены в отчёте задачи; они не являются гарантией для последующих изменений.

Сборки находятся в `apps/<имя>/dist`. Сборка web автоматически запускает [scripts/verify-web-build.js](scripts/verify-web-build.js), который проверяет имена и содержимое текстовых ресурсов на mock-worker, маркеры MSW и тестовых данных. Проверка не отключает копирование публичных ресурсов и не заменяет аудит всех возможных способов подключения моков. Для дополнительной проверки production при mock-mode:

```powershell
npm exec --workspace @zarya/web -- vite build --mode mock
node scripts/verify-web-build.js
```

Playwright проверяет стартовые оболочки и ширины 320/768/1024/1440 px, а не полноценную интеграцию новостей. Перед первым запуском нужен `npx playwright install chromium`. Команда `npm run test:e2e` запускает три обычных dev-сервера; уже работающие серверы не переиспользуются. Длительные браузерные проверки выполняются по правилам [AGENTS.md](AGENTS.md).

Исторические результаты запусков не подтверждают текущее состояние. В задаче обновления документации проверки указываются отдельно в отчёте; браузерная и серверная интеграция не подразумеваются.

## Архитектура и статус перехода

Целевой подход: FSD отдельно в каждом приложении. Публичное приложение web использует app, pages, entities и shared; CMS и модерация пока сохраняют прежнюю структуру. Правила находятся в [архитектуре](docs/ARCHITECTURE.md), последовательность переноса в [плане миграции](docs/MIGRATION.md), поведение интерфейсов и расхождения с новым проектом API в [требованиях](docs/REQUIREMENTS.md).

В PowerShell при блокировке npm.ps1 используйте npm.cmd с теми же аргументами. Предпросмотр готовой web-сборки: npm run preview --workspace @zarya/web, адрес http://127.0.0.1:6173. Предварительно выполните npm run build.

План MIGRATION.md временный. После базового переноса его сведения распределяются между архитектурой, требованиями, ADR и этой инструкцией; файл и ссылки на него удаляются.

## Публичные страницы

Главная / содержит общую навигацию с мобильным меню, вводный экран и до трёх последних новостей. Страница /news использует сетку карточек и загрузку по 12 записей, сохраняет карточки при ошибке и допускает повтор запроса. На обеих страницах работают состояния загрузки, ошибки и пустого списка. Данные получаются через один API-адаптер в entities/news; в mock-режиме используются существующие сценарии MSW.

Макет использует тёмную палитру, жёлто-оранжевые и фиолетовые акценты и декоративный мотив карты. Это базовые страницы: полноценные материалы об игре, FAQ, обновления, PressKit и детальная новость в этот этап не входят. Карточки не ведут на отсутствующий маршрут материала. Отдельная страница 404 пока не создана.
