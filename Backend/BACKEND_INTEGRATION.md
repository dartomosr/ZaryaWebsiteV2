# Интеграция серверной части вебсайта «ЗАРЯ»

Состояние сверено с исходниками 28.10.2026. Документ описывает границу frontend/API, а не внутреннее устройство серверных классов, сервисов, EF Core или схемы БД. Общий обзор находится в [README](../README.md), функциональные требования интерфейсов в [архитектуре frontend](../Frontend/ARCHITECTURE_Frontend.md), запуск и моки в [README frontend](../Frontend/README_Frontend.md).

## 1. Статусы и границы реализации

Статус контракта и состояние его реализации учитываются отдельно:

- **Предложен:** предварительный вариант для обсуждения; может использоваться в разработке frontend/MSW.
- **Согласован:** frontend- и backend-разработчики подтвердили конкретную версию маршрутов, DTO и поведения. Одобрение frontend-этапа владельцем проекта само по себе этот статус не устанавливает.
- **Реализован и проверен:** указаны конкретные стороны и среда проверки. Проверка с MSW не считается проверкой настоящего сервера.

| Область | Статус контракта | Реализация и проверка |
| --- | --- | --- |
| Список новостей `GET /api/news` | Предложен; одобрен владельцем проекта для frontend-разработки | Реализован во frontend/MSW, покрыт автоматическими тестами; реальный backend не проверен |
| Формат ошибок списка новостей | Предложен | MSW формирует 400/503; текущий клиент использует только HTTP-статус, тело ошибки не разбирает |
| Сессия, роли, регистрация, профиль | Маршруты и DTO не предложены; требования ниже | Не реализованы, CMS и модерация остаются закрытыми |
| Остальные операции новостей, обновлений, комментариев, реакций и изображений | Маршруты и DTO не определены | Целевой функционал; обработчики не созданы |
| Физические схемы `News`/`Updates` | Не согласованы | SQL-скрипты и серверные миграции не создавались |

Подтверждения серверного контракта от backend-разработчика в доступных материалах нет. При согласовании фиксировать здесь версию/дату, участников, точные изменения и среду последующей проверки. Сейчас не заявляется ни один контракт, согласованный обеими сторонами.

## 2. Система и ответственность

Три независимых React/JSX/Vite-приложения используют единый ASP.NET Core API: публичный сайт `apps/web`, CMS `apps/cms`, модерация `apps/moderation`. Они имеют собственные сборки и API-слои; SQL Server и файловое хранилище доступны через сервер. Статические описание игры, FAQ, ссылки и PressKit входят в публичную сборку. JSON используется для данных, `multipart/form-data` предусмотрен для изображений. Размещение приложений и API на реальных доменах пока открыто.

| Область | Ответственность |
| --- | --- |
| React-приложения, стили, API-адаптеры, JSDoc, MSW, клиентские тесты | Frontend |
| Серверные endpoint, бизнес-логика, права, валидация, файлы, EF Core, миграции и серверные настройки | Backend |
| Отдельные T-SQL-скрипты только `News` и `Updates` | Закреплённая frontend-зона после совместного согласования схемы; не миграции EF Core |
| `Users`, `Comments`, `NewsReactions` и остальные таблицы | Backend/владелец БД; не зона frontend-изменений |
| Имена, типы, PK/FK, индексы, каскады, модель секций обновления, даты/статусы и совместимость с EF Core | Согласуются совместно до написания DDL для `News`/`Updates` |
| Применение SQL к БД | Только явно разрешённая среда и согласованная процедура с сохранением данных и возможностью отката |

Frontend-задачи не разрешают менять backend, его инфраструктурные настройки или миграции. При несовместимости API оформляется запрос ответственному за сервер. Создание данного документа является отдельным разрешённым действием и не расширяет права изменения `Backend/`.

Подписки, рассылки, почтовые уведомления, подтверждение email письмом и флаг «Оповестить» не входят в текущий объём. Email учётной записи сохраняется. UI-правила и валидация перечислены в архитектуре; этот документ не добавляет новых функций.

## 3. Список опубликованных новостей: предварительный контракт

### 3.1. Запрос

```http
GET /api/news?page=1&pageSize=12
Accept: application/json
```

Base конфигурируется `VITE_API_BASE_URL` и включает API-префикс. По умолчанию `/api/` разрешается относительно origin публичного сайта; функция добавляет завершающий `/` и путь `news`. Для другого origin используется абсолютный base, например `https://api.example.test/api/`. Это пример, не адрес готового сервера. Vite proxy к backend сейчас не настроен.

| Параметр | Тип | По умолчанию | Ограничения |
| --- | --- | --- | --- |
| `page` | Целое число | 1 | От 1 |
| `pageSize` | Целое число | 12 | От 1 до 50 включительно |

Операция публичная, без обязательной сессии, возвращает только опубликованные материалы. Предложена сортировка по `publishedAt` по убыванию, при равенстве по `id` по возрастанию. Строковый `id` непрозрачен для frontend и не определяет SQL-тип ключа. Правило сравнения при равных датах ещё требует подтверждения; MSW содержит уже упорядоченные записи с разными датами и не проверяет серверную сортировку или фильтрацию черновиков.

### 3.2. Ответ 200 и DTO

```json
{
  "items": [
    {
      "id": "mock-news-001",
      "title": "Тестовая новость 001",
      "summary": "Вымышленный материал для разработки интерфейса.",
      "coverUrl": null,
      "publishedAt": "2026-10-26T12:00:00.000Z"
    }
  ],
  "page": 1,
  "pageSize": 12,
  "nextPage": null
}
```

Пример содержит вымышленную запись. Описания типов находятся в [news.contract.js](../Frontend/apps/web/src/api/news.contract.js), проверка ответа в [news.js](../Frontend/apps/web/src/api/news.js), mock-поведение в [mocks/news.js](../Frontend/mocks/news.js).

| Поле | Тип и ожидаемое поведение |
| --- | --- |
| `items` | Массив карточек, не больше запрошенного `pageSize` |
| `page`, `pageSize` | Числа, совпадающие с запрошенными значениями |
| `nextPage` | Следующая страница (`page + 1`) или `null`; произвольный курсор сейчас не поддерживается |
| `items[].id` | Непустая строка; уникальна внутри страницы |
| `items[].title`, `items[].summary` | Строки; код не задаёт ограничения длины для ответа |
| `items[].coverUrl` | `null` либо URL, разрешающийся в HTTP/HTTPS; при `null` картинка не отображается |
| `items[].publishedAt` | ISO 8601 UTC с `Z`; текущая проверка требует строку с `Z` и распознаваемую дату |

Дата в карточке сейчас отображается по календарю UTC. Строка даты с часовым смещением вместо `Z` текущим валидатором отклоняется. Относительный `coverUrl` разрешается браузером от страницы сайта, а не от API base. Для раздельных origin нужен абсолютный URL либо явно согласованный способ раздачи изображений. Дополнительные JSON-поля клиентом не используются. Полный текст, автор, комментарии и реакции в DTO списка не входят.

Пустая страница, в том числе за пределами списка, возвращает `200`, `items: []`, `nextPage: null`. `total` пока не требуется. Пустой массив с ненулевым `nextPage`, повторяющиеся id внутри страницы или неподходящая структура приводят к ошибке загрузки.

Клиент добавляет следующую страницу, устраняет повторные id относительно ранее загруженных карточек и сохраняет карточки при ошибке подгрузки. Кнопка блокируется на время запроса и исчезает при `nextPage: null`; повтор запрашивает ту же страницу. Новые публикации между запросами могут сдвигать страницы: текущая схема не гарантирует снимок данных или отсутствие пропусков. Курсорная пагинация этим этапом не предусмотрена.

### 3.3. Ошибки

Предложенный формат: `{ code: string, message: string, errors?: Record<string, string[]> }`. Пример `400`:

```json
{
  "code": "INVALID_QUERY",
  "message": "Некорректные параметры запроса.",
  "errors": {
    "page": ["Значение должно быть целым числом от 1."]
  }
}
```

Для `pageSize` MSW использует сообщение «Значение должно быть целым числом от 1 до 50.». Ответ `503`:

```json
{
  "code": "SERVICE_UNAVAILABLE",
  "message": "Сервис временно недоступен."
}
```

Текущий API-слой проверяет параметры до запроса, обрабатывает любой `!response.ok`, сетевую ошибку, неправильный JSON и неподходящий DTO как ошибку загрузки. Он **не разбирает `code`, `message` и `errors` из ошибочного ответа** и не различает 401/403 для этой операции. UI показывает «Не удалось выполнить операцию. Повторите попытку позже». Отменённый запрос при уходе со страницы не показывается как ошибка.

Формат полевых ошибок будущих форм, статусы конфликтов, отсутствующих материалов и отказа в доступе ещё требуется согласовать. Новые endpoint или коды для этих операций здесь не назначаются.

## 4. Авторизация и безопасность: целевые требования

Следующие требования относятся к будущим операциям; соответствующих запросов и mock-сессий сейчас нет.

- Сессия устанавливается серверной cookie. Регистрация завершается сообщением об успехе и переходом ко входу; вход по email или имени и паролю, выход с переходом на главную. Профиль позволяет менять имя, email, пароль и аватар.
- До показа CMS API подтверждает `Admin`, до показа модерации `Moderator`. Сервер проверяет права каждой операции независимо от видимости кнопок и клиентского guard. Доступ Admin к модерации и Moderator к CMS автоматически не предполагается.
- Комментирование требует активной сессии; пользователь удаляет только свой комментарий. Реакции относятся только к новостям, взаимоисключаются и снимаются повторным выбором. Доступ к реакциям и точное поведение без сессии ещё нужно определить.
- Для cookie нужно определить имя, область Domain/Path, время жизни, выход, истечение сессии, `HttpOnly`, `Secure`, `SameSite` и допустимые origin в выбранной схеме развёртывания. Значения не фиксируются без серверного контракта.
- При credentialed cross-origin запросах потребуются явные разрешённые origin и поддержка credentials сервером и клиентом; wildcard origin для такого режима не подходит. **Сейчас `getNews` не задаёт `credentials`: действует стандартное поведение fetch `same-origin`.** Передача cookie между разными origin не реализована.
- Для изменяющих состояние cookie-запросов требуется согласованная защита CSRF: способ выдачи/передачи токена или иной выбранный механизм, проверка на сервере и обработка отказа. Ни токен, ни endpoint, ни название заголовка здесь не назначены. Cookie SameSite и CORS сами по себе не подтверждают готовую защиту.
- API-отказы должны допускать клиентскую обработку без разбора HTML входа. Разделение 401/403, JSON-формат, получение текущей сессии и возврат после входа остаются открытыми.
- Секреты не помещаются в `VITE_*`. Сервер повторно проверяет данные, MIME/размер изображений и права; клиентская валидация не заменяет серверную. Время публикации задаёт backend.

Точные правила клиентских полей, загрузок и нефункциональные требования сохранены в [архитектуре frontend](../Frontend/ARCHITECTURE_Frontend.md). Внутренняя организация ASP.NET Core и EF Core остаётся решением серверной части.

## 5. Переход с MSW на реальный API

1. Подтвердить контракт списка: base, путь, query, DTO, `Z`/UTC, URL обложек, порядок, пагинацию и ошибки. Зафиксировать статус «согласован» только после подтверждения обеих сторон. При различиях сначала обновить предложение, затем отдельно согласовать изменения API-адаптера/MSW и тестов.
2. Подготовить доступный тестовый backend и публикацию изображений. SQL применять только по отдельной разрешённой процедуре; mock-данные в реальную БД автоматически не переносятся.
3. Задать `VITE_API_BASE_URL` в локальном окружении frontend, выключить `VITE_ENABLE_MOCKS` в общих локальных настройках и использовать обычный `npm run dev:web`. При необходимости перезапустить Vite. Команда `dev:web:mock` остаётся независимым режимом разработки.
4. Проверить на настоящем API первую/последнюю/пустую страницу, порядок, отсутствие черновиков, изображения, ошибку следующей страницы и повтор, отмену запроса, невалидные параметры и безопасные ошибки. Для cross-origin проверить реальное CORS-поведение браузера. Моки такие проверки не заменяют.
5. Записать среду, дату и результаты; только тогда отметить «реализован и проверен» для конкретной интеграции. Будущие операции подключать по одному разделу, с отдельным согласованием cookie/CSRF и ролей.

При несовместимости frontend-исполнитель останавливает затронутую интеграцию и сообщает ожидаемый/фактический запрос и ответ без секретов. Исправления серверного кода выполняются в серверной зоне ответственности, а не как обходная frontend-правка.

## 6. Открытые вопросы

| Вопрос | Что требуется определить |
| --- | --- |
| Контракт списка новостей | Подтверждение пути, DTO, page/pageSize/nextPage, сортировки при равных датах и формата ошибок |
| Развёртывание | Origins трёх приложений и API, HTTPS, API base, раздача статических файлов и fallback для `/news` |
| Изображения и даты | Абсолютные или относительные coverUrl, доступность с origin сайта, UTC/локальное отображение, будущий формат текста |
| Сессия и роли | Endpoint/DTO сессии, регистрация/вход/выход/профиль, проверки ролей, поведение 401/403, матрица Admin/Moderator |
| Cookie/CORS/CSRF | Конкретные параметры, credentials, разрешённые origins и заголовки, механизм защиты изменяющих запросов |
| Следующие операции | Новости по id, Updates, черновики/публикация, комментарии, реакции, изображения; маршруты и DTO пока отсутствуют |
| News/Updates и БД | Типы, связи, индексы, секции обновлений, удаление связанных данных, совместимость с EF Core, тестовая БД и порядок применения скриптов |
| Материалы игры | Утверждённые тексты, изображения, социальные ссылки, FAQ и PressKit ZIP; наличие не подтверждено |

Эти вопросы не блокируют текущую независимую разработку списка с MSW, но блокируют подтверждение полноценной интеграции. Требования к функции не следует принимать за уже согласованный HTTP-контракт.
