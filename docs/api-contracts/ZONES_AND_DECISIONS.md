# Границы трёх зон и статус решений

## Зона 1: фундамент — максимально стабильный контракт

**В этой редакции подробно спроектирована.** 33 операции: `Auth`, `Email`, `TwoFactor`, `OwnerRecovery`, `Recovery`, `Profile`, `AdminUsers`, `Owner`.

| Уровень основания | Что относится |
| --- | --- |
| **[С] Утверждённое пользователем** | Один Owner; передача с 2FA; роли; обязательная 2FA у staff; контроль email; ограниченный вход до верификации; ручной запуск восстановления пароля с email-ссылкой; запасные коды; аварийный offline key + пароль + email для Owner; удаление аккаунта с выбором судьбы комментариев |
| **[Б] Старое действовавшее требование** | ASP.NET Core + EF Core + SQL Server, серверная cookie, вход по email/имени, самостоятельные профиль и аватар, базовые ограничения регистрации |
| **[Т] Делегированная техническая конструкция** | Раздельные состояния сессии, отдельный логин `username`, двойной контроль CSRF/Origin, публичный GET сессии, единый формат ошибок, серверные права, токены, инвалидизация сессий, ограничения на повторные попытки |
| **[П] Предложено в OpenAPI, требуется согласование backend** | Любые конкретные HTTP-path, operationId, DTO/поле, cookie-name, типы полей, TTL, способ кодирования ролей, способы миграции и развёртывания |

**Особые вопросы согласования без нового продуктового опроса:**

1. Реальные origins трёх frontend-приложений и API. До этого нельзя окончательно зафиксировать SameSite, Domain и CORS.
2. Значение уникального `username` отдельно от `displayName`; текущая архитектура с ним не работала и потребует изменения формы регистрации.
3. Восстановление доступа с человеческой проверкой email: кто фиксирует факт проверки и как безопасно подтверждает её в админской операции. Поле `userEmailOwnershipVerified` — **не** автоматическое доказательство владения email; процедура требует отдельного регламента и логирования.
4. Сроки действия сессий/токенов, способ хранения TOTP-секретов, жизненный цикл ключей и безопасность аварийного восстановления. Привлечь backend/security-review.
5. Ограничения на профиль, типы avatar URL, формат ошибок и значения кодов, надёжность доставки писем, отказоустойчивость фоновых задач.
6. Уровень .NET / используемый механизм OpenAPI, согласование контроллеров и генератора серверной спецификации.

## Зона 2: основной — вероятно сохранится, но допускает корректировки

**Не проектировать вымышленные маршруты раньше договорённости о содержимом DTO.** Предлагаемый объём следующего этапа:

- Публичные новости, обновления, карточки и детали; `GET /api/news` из старого frontend/MSW уже описан как предварительный в `core.yaml`.
- Черновики, отложенная публикация, правки опубликованного через черновик, корзина, восстановление, дельта-история; отдельная форма обновлений из четырёх разделов.
- Комментарии новостей и обновлений с одним уровнем ответов, выключение комментариев, модерация и баны на комментирование.
- Фирменные реакции **только** на новости.
- FAQ, общий каталог изображений, базовые материалы страницы PressKit и собственный профиль по медиа.

В `core.yaml` сейчас **только один** предварительный endpoint, а не контракт всего перечисленного объёма.

## Зона 3: расширенный — структура может существенно меняться

**Пока без операций в YAML:**

- Мировая Машина: получение текста фиксированных объектов единым набором при входе, версия набора и кэширование без API-запроса на каждый зум/клик, без возможности CMS менять геометрию.
- Пакетная атомарная публикация нескольких информационных материалов (FAQ, описания, PressKit, тексты Мировой Машины).
- Генерация ZIP PressKit из ровно того опубликованного набора, который видит пользователь.
- Сложные редакторские инструменты (превью пачки, сравнение/разрешение конфликтов нескольких материалов), если они потребуют отдельных технических ресурсов.

**Обязательность этих функций не снижается из-за высокой изменчивости схемы API.** Их следует разрабатывать позже, но включать в план работ уже сейчас.

## Правила изменения

1. **Предложен** — свободно редактируется после обсуждения, не совместимый с реальным backend.
2. **Согласован** — frontend и backend оба подтверждают точную версию API; регистрация решения в CHANGELOG обязательна.
3. **Реализован и проверен** — интеграционные тесты на настоящем сервере, с датой, средой и результатами, а не только MSW.
4. **Зона 1 после согласования** — ломающие изменения только с версионированием и миграцией.
5. **Зона 2 после согласования** — согласованные изменения вместе с frontend API адаптерами/тестами.
6. **Зона 3 до согласования модулей** — можно перерабатывать схемы, обязательно обновляя описание и решения.
