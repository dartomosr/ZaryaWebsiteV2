# Комментарии, реакции и модерация

[Оглавление](../README.md) · [Примеры](EXAMPLES.md)

Источники: [comments.yaml](../core/comments.yaml), [reactions.yaml](../core/reactions.yaml), [moderation.yaml](../core/moderation.yaml). Публичный автор содержит id, displayName, avatarUrl и deleted. Email и username публично не выдаются.

## Комментарии

GET `/api/news/{newsId}/comments` и аналог updates возвращают корневые комментарии. GET `/api/comments/{rootCommentId}/replies` возвращает плоский список ответов. Для ответа на ответ `rootId` остаётся id корня, а `replyToCommentId` указывает адресата. Backend проверяет принадлежность материалу и ветке, а не только существование id.

POST соответствующей коллекции принимает `text`, `rootId`, `replyToCommentId`. Для корня оба id равны null; для ответа оба заданы. Сначала получить сессию/CSRF и публичный материал, затем отправить текст. Нужны `active`, подтверждённый email, отсутствие бана и включённые комментарии. Текст после trim имеет 1–1000 символов; HTML и Markdown комментариев не становятся исполняемой разметкой. Публикация немедленная, премодерации нет.

PATCH `/api/comments/{commentId}` меняет только собственный текст без временного лимита; бан запрещает редактирование. DELETE этого пути позволяет автору удалить свой текст даже при бане. Ответы других не удаляются: при сохранённой ветке остаётся заглушка с `text:null`. `isPlaceholder` нельзя использовать как разрешение восстановить скрытый текст.

Прямой запрос к обсуждению скрытого материала также даёт 404. Это закрывает обход через дочерние id. Порядок комментариев, поведение авторского удаления уже скрытого материала и защита от потери двух параллельных правок текста требуют согласования. Текущий PATCH не принимает версию; сериализация на сервере исключит повреждение данных, но сама по себе не предотвратит last-write-wins.

## Реакции

GET `/api/reactions/types` возвращает существующий каталог фирменных реакций. Конкретные значения не выдумываются. GET `/api/news/{newsId}/reactions` выдаёт счётчики и `myReactionTypeId` для active-сессии, иначе null. Ответ персонализирован и не кешируется совместно.

PUT `/api/news/{newsId}/reaction` устанавливает `typeId`, заменяя прежнюю реакцию. Повтор того же PUT не снимает её и не создаёт дубликат. Повторный выбор в UI должен вызвать DELETE этого пути. Уникальность пары пользователь/новость требуется на уровне БД. Реакций к обновлениям нет.

## Модерация

Moderator/Admin/Owner с active-сессией читают GET `/api/moderation/comments`, включая скрытые записи. Фильтр `status` поддерживает all/visible/hidden; `author_removed` виден через all. POST `/{commentId}/hide` требует тело `reason` (может быть null), POST `/{commentId}/restore` восстанавливает только модераторское скрытие. Перед hide интерфейс запрашивает пользовательское подтверждение. Успех определяется ответом сервера, а не исчезновением кнопки.

GET `/api/moderation/comment-bans` выдаёт запреты. PUT `/api/moderation/users/{userId}/comment-ban` принимает reason и expiresAt: null означает бессрочный бан, дата должна быть в будущем. DELETE того же пути снимает бан. Бан запрещает создание, ответы и редактирование, но не чтение и удаление своего текста. Возможность санкций против сотрудников отдельно не уточнена исходниками; матрица ролей в аудите не расширялась и не сужалась.

## Удаление аккаунта и гонки

POST `/api/me/delete` принимает выбор `keep_anonymized` либо `erase_text`. Реакции удаляются, чужие ответы сохраняются. При erase_text нельзя вернуть текст через модерацию, историю, кеш или фоновые задачи. Проверка состояния и restore атомарны со стиранием; после стирания restore даёт 409. При keep_anonymized прежний автор обозначается удалённым, без обратной публичной связи с аккаунтом.

Ошибки: 401 сессия отсутствует, 403 чужой текст/бан/закрытое комментирование, 404 скрытый материал, 409 невозможное восстановление, 422 невалидный текст/ветка, 429 превышение частоты. Повтор POST комментария после потери ответа может создать дубликат: механизма идемпотентности здесь пока нет.
