# Устаревший multipart-парсер новостей

[Оглавление](../README.md) · [Текущий контракт Backend](NEWS_RESPONSE.md)

Этот документ сохранён как описание существующего [клиента](../../../Frontend/apps/web/src/api/news.js) и [MSW](../../../Frontend/mocks/news.js), которые пока ожидают `multipart/mixed`. Он больше **не описывает контракт Backend**: актуальный ответ — JSON DTO, см. [NEWS_RESPONSE.md](NEWS_RESPONSE.md). Клиентскую реализацию эта редакция не меняет.

## Запрос и метаданные

`GET /api/news?page=1&pageSize=12`, `Accept: multipart/mixed`. Операция публичная. Параметры и сортировка описаны в [архитектуре](ARCHITECTURE.md#пагинация).

Ответ 200 имеет `Content-Type: multipart/mixed; boundary="zarya-example-boundary"`. Boundary может быть заключён в кавычки либо передан допустимым token. Выбирается ASCII-строка длиной 1–70 символов, без CR/LF; перед выдачей исключается совпадение разделителя с содержимым частей. Это соответствует [RFC 2046, раздел 5.1.1](https://www.rfc-editor.org/rfc/rfc2046#section-5.1.1).

Ниже текстовый пример страницы без изображений. Каждая граница и строка заголовка завершается **CRLF**, пустая строка отделяет заголовки части от тела. В Markdown визуально показываются переносы, фактический wire-тест создаёт байты CRLF.

```text
HTTP/1.1 200 OK
Content-Type: multipart/mixed; boundary="zarya-example-boundary"
Cache-Control: no-store

--zarya-example-boundary
Content-Type: application/json; charset=utf-8
Content-ID: <metadata>

{"items":[{"id":"example-news-1","title":"Пример","summary":"Текст примера.","coverPartId":null,"publishedAt":"2026-11-02T19:00:00Z"}],"page":1,"pageSize":12,"nextPage":null}
--zarya-example-boundary--
```

Для пустой страницы metadata содержит `items:[]`, фактические page/pageSize и `nextPage:null`. Это полноценный 200 с одной JSON-частью, а не пустое HTTP-тело или 204.

## Сопоставление обложек

Первая часть всегда имеет `Content-ID: <metadata>` и `Content-Type: application/json` с необязательным charset=utf-8. Её JSON строго соответствует NewsPage. Для обложки поле coverPartId содержит **полное значение с угловыми скобками**, например `<news-123@zarya>`.

Каждая обложка передаётся отдельной следующей частью:

```text
--zarya-example-boundary
Content-Type: image/png
Content-ID: <news-123@zarya>

[бинарные байты изображения, не base64 и не этот поясняющий текст]
```

Порядок изображений после metadata несущественен: клиент сопоставляет по Content-ID. Допускаются только image/jpeg, image/png и image/webp с непустым телом. У части ровно один Content-ID; значения уникальны. Каждая ненулевая ссылка карточки использует ровно одну часть, каждая часть используется ровно одной карточкой. Даже одинаковая обложка двух карточек передаётся двумя частями с разными Content-ID: текущий клиент удаляет найденную часть из таблицы и не поддерживает повторное использование id. `coverPartId:null` не требует части.

Закрывающая граница `--boundary--` обязательна, допускается финальный CRLF. Preamble, epilogue, переносы LF без CR, folded headers и Content-Transfer-Encoding не используются. Это профиль совместимости существующего парсера, а не утверждение, что MIME вообще запрещает эти возможности. Не передавать отдельные HTTP-статусы внутри частей.

## Ошибки и восстановление

До начала успешного тела сервер может вернуть JSON Error с 400/429/500/503. Если поток 200 уже начат и произошёл сбой, нельзя дописать JSON-ошибку внутрь multipart и считать ответ успешным: прервать поток. Клиент отклоняет неполное тело целиком и не применяет часть карточек.

Отсутствующая/повторная/лишняя часть, неизвестный Content-ID, неверный MIME, повреждённый JSON, незакрытая граница и несогласованная пагинация приводят к ошибке загрузки. При ошибке следующей страницы существующий UI сохраняет предыдущие карточки и повторяет ту же страницу. Отмена через AbortSignal не показывается как обычная ошибка.

## Размер, поток и кеш

Сервер может записывать части последовательно, но текущий клиент вызывает response.arrayBuffer(), затем создаёт копии байтов и Blob. Он **не является потоковым парсером** и пока не ограничивает общий размер ответа, длину заголовков, число MIME-частей или число пикселей. Ограничение pageSize до 50 не решает проблему: 50 обложек по 5 MiB уже дают около 250 MiB до дополнительных копий.

Совместимый вариант для согласования: выдавать оптимизированные обложки и ограничить общий бюджет ответа до записи первых байтов, сохранив NewsPage и multipart. Численные лимиты нужно согласовать с backend; их нельзя объявлять реализованными. Защита самого клиента от чрезмерного тела требует отдельного изменения Frontend, запрещённого текущей задачей.

Для текущего клиента описан Cache-Control: no-store, условный GET и 304 не добавлены. Если понадобится кеширование, потребуется согласовать хранение полного тела и обработку 304; это не повод менять media type. Пагинация остаётся page/pageSize и не гарантирует стабильный снимок между запросами.

## OpenAPI и проверки

В OpenAPI 3.0.3 ответ представлен как `type:string`, `format:binary`, media type multipart/mixed. Динамическое число частей и связи Content-ID текстовая схема не проверяет. `encoding` применяется к requestBody и не решает моделирование такого ответа. Основание: [Media Type Object OAS 3.0.3](https://spec.openapis.org/oas/v3.0.3#media-type-object).

23 [регрессионных теста](../tests/multipart.test.js) вызывают существующий getNews без изменения Frontend: пустая страница, отсутствие изображения, сохранность бинарных байтов, кавычки boundary и 19 повреждённых/несогласованных вариантов. Команда из корня репозитория:

```powershell
node Frontend/node_modules/vitest/vitest.mjs run --config docs/api-contracts/tools/vitest.config.mjs
```

Это проверка клиентского парсера с синтетическими HTTP Response, не тест настоящего ASP.NET endpoint. Проверка семантики изображения, объёмов памяти и потоковой серверной выдачи не проводилась.
