# Источники требований и решения

[Оглавление](../README.md) · [Аудит](../API_AUDIT_REPORT.md)

## Приоритет и достоверность

1. Прямое задание пользователя на этот аудит, включая четыре раздела обновлений, email-подтверждение, 2FA, единственного Owner и границы изменений.
2. Реализация Backend, когда она доступна; для `GET /api/news` текущий контроллер возвращает JSON DTO с сериализованным `PhysicalFileResult`.
3. Согласованные технические решения с доступным первоисточником.
4. Текущие предложенные YAML и руководства как проверяемый проект API.
5. Историческая документация как описание прежнего этапа.

Функциональное ТЗ 0.2 и итоговый аудит требований 0.2 упоминаются в старых материалах, но их отдельные файлы в репозитории не найдены. Поэтому утверждения старых руководств «утверждено пользователем» не являются независимым подтверждением полного ТЗ. Аудит сопоставляет все сценарии приложенного задания; полная трассировка отсутствующего ТЗ не заявляется.

## Утверждённые решения R04 (02.11.2026)

Владелец проекта окончательно утвердил уникальный без учёта регистра ASCII `username`, вход по username или email через одно поле `login` и отдельный изменяемый `displayName`. Символ `@` уже запрещён шаблоном username, поэтому наличие `@` однозначно выбирает поиск только по email, отсутствие поиск только по username. Уникальность обеспечивается атомарно, включая конкурентные регистрации. Пароль, 2FA и ограниченный режим до подтверждения email сохраняются.

При передаче владения новый владелец получает `owner`, прежний получает `user` независимо от прежних административных полномочий. Изменение атомарно, Owner ровно один, подтверждение паролем и TOTP и отзыв прежних привилегированных сессий обязательны. R04 закрыт на уровне контракта; это не подтверждение реализации backend и не изменение статуса остальных решений.

## Вопросы до заморозки

| Вопрос | Предпочтительный вариант и последствия |
|---|---|
| Origins, cookie, TTL, CORS | Один origin через reverse proxy снижает сложность. Для разных origin понадобится credentialed CORS и согласованный SameSite |
| Recovery-регламент | Проверка контроля email человеком с журналом; boolean API сам по себе недостаточен |
| Idempotency-Key | Для пакета хранить результат вместе с commit, определить TTL; для create news/comment обсудить отдельное расширение |
| Объём ответов | Утвердить бюджет непагинируемых наборов и ZIP, а также лимиты пикселей/файлов |
| Пагинация | Для текущего news сохранить page/pageSize. При требовании отсутствия пропусков отдельно согласовать cursor/snapshot |
| Сортировка | Закрепить вторичные ключи и SQL collation, направление комментариев и CMS-списков |
| Редактирование комментариев/банов | Решить допустимость last-write-wins либо добавить версии совместно с UI |
| FAQ discard | Уточнить отмену stage-delete и удаление первого черновика без публикации |
| Медиа и старые ZIP | Определить защищённую выдачу неопубликованных файлов, сроки хранения и очистки закреплённых снимков |
| zipUrl=null | Для полноценного PressKit предпочтительно требовать готовый ZIP на каждой публикации; nullable пока сохранён для совместимости этапов |
| Мировая Машина | Утвердить реестр ключей и синхронизацию выпусков frontend/backend, без CMS-редактирования структуры |
| Антиenumeration | Согласовать ответы регистрации/восстановления и rate limits, сохранив удобство исправления полей |

## Изменение статуса

`proposed` не равно `agreed`. Для согласования фиксируют версию, дату, участников и точные исключения. Для `implemented-and-verified` дополнительно нужны среда и результаты интеграции. Foundation после согласования защищается строже, Core меняется с потребителями, Extended допускает более свободное развитие, но не отменяет обязательность функций. Ни одна зона в аудите не объявлена согласованной.
